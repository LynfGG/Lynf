# Internationalisation

Lynf ships in **English and French** from the start.

## Keys, always

**No user-facing string is hardcoded.** Every one of them goes through `t('key')`.

```tsx
// Avoid
<h2>Ranked Solo/Duo</h2>

// Prefer — with t from useTranslation('summoner')
<h2>{t('profile.rankedSoloTitle')}</h2>
```

This includes short strings, button labels, placeholders, `aria-label` values and error messages.
A string that escapes the mechanism is invisible until someone switches language.

## Files and keys

**One file per domain and per language.** A single large file becomes unmergeable and impossible
to review.

```
src/i18n/
├─ en/
│  ├─ common.json
│  └─ summoner.json
└─ fr/
   ├─ common.json
   └─ summoner.json
```

Each file is an i18next **namespace**, named after its domain: a component picks it with
`useTranslation('summoner')`. `common` is the default namespace, for what belongs to no domain —
the application name, the language switcher, the legal notice.

Inside a file, keys are named

```
<screen or component>.<element>
```

in `camelCase` — for example `profile.rankLabel`, `search.submit`, `errors.rateLimited`. Reaching
into another namespace spells it out: `t('common:appName')`.

Without a rule, `summonerRankTitle` and `profile.rank.label` end up side by side within weeks.

## Language selection

The detector reads the browser language and **falls back to English** when it finds anything else,
and when a key is missing from the selected language. The interface carries a language switcher —
without one, the second language is unreachable and therefore pointless. The page's `lang`
attribute follows the selected language.

## Key parity is checked by CI

The real risk of shipping two languages is the two sets drifting apart under time pressure.

**CI compares the key sets of both languages and fails when one holds a key the other does not.**
This is not a review responsibility: adding a string means adding it in both files, and the build
says so before a human has to.

## Formatting values

Never assemble dates and numbers by hand — separators, ordering and plural rules differ by locale,
and hand-rolled formatting is wrong in at least one of them. Let the translation format them, with
i18next's built-in formatters, which use `Intl` in the current language:

```json
{ "level": "Level {{level, number}}", "updatedAt": "Updated {{when, datetime}}" }
```

```tsx
t('profile.updatedAt', {
    when: new Date(profile.updatedAt),
    formatParams: { when: { dateStyle: 'medium', timeStyle: 'short' } },
});
```

A value is never glued to a translated label (`{t('levelLabel')} {level}`): word order differs
between languages too.

## Right-to-left is out of scope

RTL layout support is deliberately not implemented. It would only serve languages the product does
not target, and it would constrain every margin and padding decision for no benefit.

This is a conscious exclusion, not an oversight. Revisit it only if such a language is actually
planned.

## The Riot legal notice is never translated

Riot requires this text verbatim, in a location readily visible to players. The wording is imposed:
translating it would breach their policies.

> Lynf isn't endorsed by Riot Games and doesn't reflect the views or opinions of Riot Games or
> anyone officially involved in producing or managing Riot Games properties. Riot Games, and all
> associated properties are trademarks or registered trademarks of Riot Games, Inc.

It is therefore identical in both language files.
