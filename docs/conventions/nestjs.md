# NestJS

[Official documentation](https://docs.nestjs.com/)

## Module layout

Every domain module follows the same structure:

```
src/
└── [module-name]/
    ├── controllers/         *.controller.ts
    ├── services/            *.service.ts
    ├── repositories/        *.repository.ts
    ├── externals/           *.external.ts
    ├── decorators/          *.decorator.ts
    ├── dtos/                *.dto.ts
    ├── enums/               *.enum.ts
    ├── types/               *.ts
    ├── utils/               *.utils.ts
    └── [module-name].module.ts
```

`main.ts` and `app.module.ts` sit at the root of `src/`: one boots the application, the other
assembles the modules.

### Naming

Class names carry the suffix of their kind, and so do file names:

| Kind       | Class suffix | File suffix       |
| ---------- | ------------ | ----------------- |
| Controller | `Controller` | `*.controller.ts` |
| Service    | `Service`    | `*.service.ts`    |
| Repository | `Repository` | `*.repository.ts` |
| External   | `External`   | `*.external.ts`   |
| Provider   | `Provider`   | `*.provider.ts`   |
| Module     | `Module`     | `*.module.ts`     |
| DTO        | `Dto`        | `*.dto.ts`        |
| Guard      | `Guard`      | `*.guard.ts`      |
| Utils      | —            | `*.utils.ts`      |

## Layers

```
Controller ──▶ Service ──▶ Repository ──▶ Database
                  │
                  └──────▶ External ────▶ third-party HTTP API
```

The chain is not short-circuited. Each layer has one job and one set of allowed dependencies.

### Controllers

HTTP only: read the request, call a service, return what it gives back.

- Every route is documented with [Swagger](https://docs.nestjs.com/openapi/introduction)
  decorators.
- Route parameters, query strings and bodies are validated by DTOs through the global
  `ValidationPipe`:

```ts
app.useGlobalPipes(
    new ValidationPipe({
        transform: true,
        forbidUnknownValues: true,
    }),
);
```

- **A controller never injects a repository or an external.**

### Services

All business logic lives here. A service may inject other services, repositories and externals.

Public methods called from controllers return the shared response type that the DTO implements —
mapping is the service's job, not the controller's.

### Repositories

All database querying lives here, and nothing else.

- **A repository depends on the database client only** — never on a service, never on another
  repository, never on an external.
- Inserts and updates run inside transactions.

### Externals

An external is the boundary with a third-party HTTP API. It exists because the application reads
from two sources — our database and the Riot API — and the layer above must not care which is
which.

- **An external depends on no service and no repository.** It knows its HTTP client and its
  configuration.
- It translates provider failures into NestJS exceptions: a provider 404 becomes a
  `NotFoundException`, a 429 is surfaced rather than swallowed, and a rejected credential becomes a
  502 — never a 401, which would tell the caller that _they_ are not authenticated.
- Every call has a deadline: a provider that hangs must not hold a request for minutes.
- It holds no business logic. Deciding _when_ to call it, and what to do with the answer, is the
  service's job.
- An external used by more than one domain lives in its own module, which exports it.

## Database schemas

Drizzle schemas are **centralised** in `src/database/schema/`.

This is a deliberate exception to the rule that everything a module needs lives in its folder: the
migration tooling requires a single schema entry point, and typing the client depends on the
complete schema object. Fighting the tooling to preserve the rule would cost more than the
exception.

Migrations are generated by the tooling and **committed** — they are reviewed like any other change.

## Validation

Two validators, one boundary:

- **`class-validator`** for DTOs — HTTP input, validated on every request.
- **Zod** for configuration — environment variables, validated once at startup.

Environment variables are always strings, so configuration needs coercion and benefits from having
its type derived from the schema; request payloads are already structured and belong to the
decorator-based pipeline. Do not mix the two.

The application **refuses to start** when a required variable is missing or malformed, rather than
failing on the first request that needs it.

## Shared types

The API contract consumed by the front end lives in `packages/shared`: **types and plain constants
only**, no classes, no decorators. DTOs are decorated classes and stay in the back end; they
implement the shared types rather than being exported.

## Errors

Prefer NestJS exceptions to plain `Error`: `NotFoundException`, `BadRequestException`,
`UnauthorizedException`, `ForbiddenException`, `ConflictException`,
`UnprocessableEntityException`, and so on.

NestJS turns them into HTTP responses on its own, so **catching is for specific intent only**:

- swallowing an error deliberately — and then it **must** be logged;
- reacting to one specific failure by throwing another, more meaningful one.

Catching to hide a problem is not one of those cases.

## Logging

Use the NestJS `Logger`, one instance per class, named after it:

```ts
private readonly logger = new Logger(SummonerService.name);
```

Never log a secret — the Riot key included.

## Tests

| Layer        | How                                                 | Why                                                                  |
| ------------ | --------------------------------------------------- | -------------------------------------------------------------------- |
| Services     | Unit, with repositories and externals stubbed       | The logic lives here                                                 |
| Repositories | Against a real test database                        | Stubbing a database only proves the stub                             |
| Externals    | Stubbed HTTP responses, asserting error translation | A 404 must become a `NotFoundException`; a 429 must not be swallowed |
| Controllers  | No unit tests                                       | They delegate; route-level tests are planned                         |

Minimum coverage is **85% on services and repositories**, not on the codebase as a whole. Covering
trivial code to reach a number proves nothing.
